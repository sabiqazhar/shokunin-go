Ringkasan dan Cara Tim Menjalankannya

Tujuannya bukan sekadar "bisa menulis REST API dengan Go", melainkan bisa menjelaskan kenapa sistem bekerja seperti itu, bisa membuktikan dengan data bahwa optimasi efektif, dan bisa mempertanggungjawabkan trade-off saat terjadi kegagalan.

Untuk siapa: engineer backend yang sudah punya pengalaman Python / Go / Docker / database. 8 jam per pekan, total 24 pekan.

Kenapa urutannya begini? Semakin ke depan, semakin tidak bisa dilewati:

  1. Memori dan GC menentukan apakah Anda bisa membaca flame graph pprof. Kalau tidak paham alokasi, profiling cuma seperti melihat gambar berwarna.
  2. Konkurensi dan Linux menentukan apakah Anda bisa menjawab "kenapa CPU tidak penuh tapi latensi melonjak".
  3. Jaringan dan storage menentukan apakah Anda paham apa yang sebenarnya terjadi di bawah abstraction framework.
  4. Sistem terdistribusi dibangun di atas tiga hal sebelumnya. Bug distributed pada dasarnya adalah tumpukan dari "konkurensi + jaringan + persistensi".

Jangan melompat. Orang yang langsung mengerjakan Raft tanpa melewati Fase 2 dan 3 akan menghadapi tiga jenis bug sekaligus: scheduling, framing, dan persistensi. Waktu debugging-nya naik secara eksponensial.

1.3 Escape Analysis: Inti Minggu Ini

Definisi satu kalimat: kalau masa hidup sebuah variabel tidak bisa dipastikan berakhir di dalam stack frame pada saat kompilasi, compiler akan menempatkannya di heap untuk diklaim kembali oleh GC. Ini disebut "escape".

flowchart TD Q["Di mana variabel v dialokasikan?"] --> A{"Apakah operator address-of dipakai pada v?"} A -- Tidak --> ST["Di stack<br/>langsung dibebaskan saat fungsi return"] A -- Ya --> B{"Apakah pointer-nya keluar dari fungsi?"} B -- "hanya dipakai di dalam fungsi ini" --> ST B -- "dikembalikan sebagai return value" --> HP["Di heap"] B -- "disimpan ke interface{} / any" --> HP B -- "ditangkap oleh closure" --> HP2["Di heap<br/>atau di konteks closure"] B -- "disimpan ke objek global atau yang sudah ada di heap" --> HP B -- "dikirim ke fungsi yang tidak dikenal<br/>tidak di-inline" --> HP B -- "ukurannya tidak diketahui saat kompilasi<br/>make dinamis" --> HP ST --> E["Nol beban GC"] HP --> F["Menghasilkan beban GC"]

Praktik: Mengamati Escape

// escape.go
package main

type Point struct{ X, Y int64 }

func stack() int64 {          // kasus 1: murni di stack
    p := Point{X: 1, Y: 2}
    return p.X + p.Y
}

func heap() *Point {          // kasus 2: mengembalikan pointer → escape
    p := Point{X: 1, Y: 2}
    return &p
}

func box() any {              // kasus 3: di-boxing jadi interface → escape
    v := int64(42)
    return v
}

func closure() func() int64 { // kasus 4: ditangkap closure → escape
    v := int64(7)
    return func() int64 { return v }
}

func main() {
    _ = stack()
    _ = heap()
    _ = box()
    _ = closure()
}

go build -gcflags="-m=2" ./escape.go 2>&1 | head -60

Anda akan melihat semacam ini:

./escape.go:8:6: can inline stack
./escape.go:17:2: p escapes to heap:
./escape.go:17:2:   flow: ~r0 = &p:
./escape.go:17:2:     from &p (address-of) at ./escape.go:18:9
...
./escape.go:23:2: v escapes to heap:
./escape.go:23:2:   flow: ~r0 = &v:
... boxed

Cara membacanya: - moved to heap: p — pasti escape - escapes to heap + rantai flow: — ini jalur escape yang diberikan compiler; ikuti alurnya dan Anda akan menemukan akar masalahnya - does not escape — tetap di stack - can inline / inlining call to — keputusan inlining

Daftar Skenario Escape yang Sering Muncul (sering ditanyakan ke tim)

Skenario Escape? Alasan
Mengembalikan pointer ke variabel lokal Ya Masa hidupnya melebihi stack frame
Disimpan ke interface{} / any Ya Interface menyimpan pointer di dalamnya (kecuali nilainya 0 atau berbentuk pointer yang bisa disimpan langsung)
Dikirim ke fungsi yang tidak di-inline (parameternya any) Ya Compiler tidak bisa melihat apa yang dilakukan pemanggil
Ditangkap closure lalu keluar Ya Konteks closure harus hidup sampai closure dipanggil
make([]T, n), n berupa variabel Biasanya escape Ukuran tidak bisa ditentukan saat kompilasi
make([]T, 100), konstanta literal dan tidak keluar Mungkin tidak escape Jadi array di stack (ada batas ukuran, sekitar 64KB, dan dipengaruhi inlining)

Argumen fmt.Sprintf("%d", x) Ya Tipe parameternya ...any
Objek besar yang melewati batas stack Ya Stack maksimal 1GB, tapi satu stack frame yang terlalu besar juga dipindah ke heap

Pengingat penting: escape bukanlah "kesalahan". Alokasi di stack itu murah, tapi yang jadi masalah adalah escape ke tempat yang tidak bisa Anda kendalikan. Constructor yang mengembalikan pointer itu sangat wajar. Masalah yang sebenarnya adalah boxing dan objek sementara yang tidak ada gunanya di hot path.

Minggu 2 · Stack, Heap, Pointer, Alokasi, dan Siklus Hidup Objek

2.1 Lapisan Memori di Go

flowchart TD subgraph G["Stack Goroutine"] S1["Stack frame<br/>argumen · return · variabel lokal"] S2["Stack kontigu: mulai 2KB<br/>tumbuh 2x atau menyusut sesuai kebutuhan"] S1 --- S2 end subgraph H["Heap"] H1["mcache<br/>milik tiap P, tanpa lock"] H2["mcentral<br/>dikelola per size class"] H3["mheap<br/>meminta arena ke OS"] H4["span / size class<br/>~67 kelas 8B sampai 32KB"] H5["Objek besar lebih dari 32KB langsung lewat mheap"] H1 --> H2 --> H3 H4 --- H1 end OS["Sistem operasi<br/>mmap / madvise"] --> H3 S2 -.escape.-> H

Poin penting:

  • Stack: tiap goroutine punya sendiri, awalnya 2KB, tumbuh dengan cara "segmented stack → stack kontinu yang disalin". Saat tumbuh, batas stack dicek (morestack) dan seluruh stack disalin — jadi rekursi dalam + stack frame besar ada biayanya.
  • Heap: dialokasikan per size class (kelas ukuran), objek kecil diambil dari free list di mcache, tanpa lock; hanya kalau melintasi P barulah masuk ke mcentral/mheap.
  • Alokasi bukan berarti system call: Go meminta satu blok besar ke OS sekaligus (arena, biasanya kelas 64MB), lalu memotong-motongnya di user space. Jadi "alokasi lambat" biasanya lambat di pemindaian GC, bukan di mmap.

2.2 Eksperimen 1: Pointer vs Value (berlawanan dengan intuisi)

Banyak orang mengira "pointer pasti lebih cepat". Untuk struct kecil, biasanya justru sebaliknya, karena pointer memaksa escape + menambah satu kali indirect addressing + membuat GC harus memindai.

// bench_test.go
package bench

Tiga Jebakan Memori yang Sering Terjadi

// Jebakan 1: slice besar dipotong lalu disimpan lama → kebocoran memori
func leak() []byte {
    big := make([]byte, 10<<20)  // 10MB
    return big[:10]              // cuma mengembalikan 10B, tapi array 10MB di bawahnya masih direferensi!
}
// Perbaikannya
func fixed() []byte {
    big := make([]byte, 10<<20)
    out := make([]byte, 10)
    copy(out, big[:10])
    return out
}

// Jebakan 2: memakai ulang buffer tapi lupa dibatasi → tumbuh tanpa batas
var pool = sync.Pool{New: func() any { return new(bytes.Buffer) }}
func reuse() {
    buf := pool.Get().(*bytes.Buffer)
    buf.Reset()               // Reset tidak mengosongkan array dasarnya
    if buf.Cap() > 1<<20 {    // kalau lewat batas, buang saja, biar pool tidak penuh benda raksasa
        pool.Put(new(bytes.Buffer))
    } else {
        pool.Put(buf)
    }
}

// Jebakan 3: append berbagi array dasar → data terkontaminasi diam-diam
a := []int{1, 2, 3}
b := a[:2]
b = append(b, 99)   // cap masih cukup → langsung mengubah a[2]!
// sekarang a adalah [1 2 99]
// Perbaikan: b := append(a[:2:2], 99)  // slice tiga indeks, memaksa alokasi baru

3.1 Representasi Interface di Level Bawah

    tab  *itab        // tipe + tabel method
    data unsafe.Pointer // menunjuk ke data sebenarnya
}
type eface struct {   // interface kosong any
    _type *_type
    data  unsafe.Pointer
}
type itab struct {
    inter *interfacetype
    _type *_type
    hash  uint32
    _     [4]byte
    fun   [1]uintptr  // sebenarnya tabel method dengan panjang variabel
}
flowchart LR subgraph VAR["Variabel interface i io.Writer"] T["tab: *itab<br/>metadata tipe + tabel alamat method"] D["data: unsafe.Pointer"] end D --> OBJ["*os.File di heap"] T --> M["Tabel method fun[0]=Write<br/>fun[1]=Close ..."] M --> IMPL["Implementasi os.File.Write"]

Kesimpulan kunci:

  1. Variabel interface = dua word (16B). Mengoper interface sebagai argumen berarti dua kali penyalinan + satu kali lompatan pointer.
  2. Pemanggilan method itu dynamic dispatch: lewat itab.fun[i], tidak bisa di-inline (Go 1.21+ punya optimisasi PGO / devirtualisasi spekulatif untuk "inlining method interface", tapi jangan berharap).
  3. Boxing bisa memicu alokasi: menaruh value non-pointer ke dalam interface butuh menyalin value itu ke heap (kecuali ia berupa word yang bisa disimpan langsung).
  4. itab punya cache global, jadi type assertion v.(T) adalah pencarian tabel hash, bukan menelusuri tipe satu per satu.

3.2 Method Set (aturan yang paling sering bikin tersandung)

Deklarasi receiver Method set dari value T Method set dari pointer *T
func (t T) M() memuat M memuat M
func (t *T) M() tidak memuat M memuat M

Konsekuensinya: apakah var i Iface = someValue bisa dikompilasi bergantung pada apakah method set dari value-nya mencakup interface itu.

type Speaker interface{ Speak() }

Saran standar tim: pada satu tipe, jangan mencampur receiver value dan receiver pointer. Semuanya value (objek value kecil yang immutable), atau semuanya pointer (punya state, berisi mutex, perlu diubah). Mencampur keduanya adalah tanda desainnya berantakan.

3.3 Generics: Kapan Benar-Benar Berguna

type Ordered interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64 |
    ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~float32 | ~float64 | ~string
}

type Ring[T any] struct {
    buf  []T
    head int
    n    int
}

func NewRing[T any](cap int) *Ring[T] { return &Ring[T]{buf: make([]T, cap)} }

func (r *Ring[T]) Push(v T) {
    r.buf[(r.head+r.n)%len(r.buf)] = v
    if r.n < len(r.buf) { r.n++ } else { r.head = (r.head + 1) % len(r.buf) }
}

Biaya dan manfaat generics (wajib diukur sendiri):

  • Generics di Go adalah campuran "kamus + template" (GCShape stenciling): tipe dengan bentuk dasar yang sama berbagi satu salinan kode + kamus di runtime.
  • Kesimpulannya biasanya: generics di container/algoritma jauh lebih cepat daripada interface{} (tanpa boxing, tanpa alokasi), mendekati kode konkret yang ditulis manual, tapi kadang sedikit lebih lambat.
  • Generics akan menambah waktu kompilasi dan ukuran binary (beberapa stencil).

Eksperimen: Perbandingan Tiga Implementasi

func SumIntsGeneric[T int64 | float64](s []T) T {
    var t T
    for _, v := range s { t += v }
    return t
}
func SumIntsConcrete(s []int64) int64 {
    var t int64
    for _, v := range s { t += v }
    return t
}
func SumIntsIface(s []any) int64 {
    var t int64
    for _, v := range s { t += v.(int64) }  // type assertion + kemungkinan alokasi
    return t
}

Ekspektasinya: Concrete ≈ Generic >> Iface. Tapi kalau hasil ukur Anda menunjukkan Generic 10% lebih lambat dari Concrete, itu normal — catat angkanya dan jelaskan (overhead stencil/kamus, inlining yang terbatas).

Minggu 4 · Garbage Collection, Laju Alokasi, dan Beban GC

4.1 Apa Itu GC di Go

Go memakai collector concurrent tri-color mark & sweep (penandaan dan pembersihan tiga warna yang berjalan konkuren):

  • Non-generational (tidak ada young generation / old generation)
  • Non-moving (tidak merapikan memori, alamat objek tidak berubah — ini sangat ramah untuk cgo dan aritmetika pointer)
  • Konkuren: fase mark berjalan bersamaan dengan kode user, hanya ada STW (Stop-The-World) yang sangat singkat
flowchart TD A["Sweep Termination<br/>STW: membersihkan sisa ronde sebelumnya"] --> B["Persiapan Mark<br/>STW: mengaktifkan write barrier"] B --> C["Mark konkuren<br/>berjalan paralel dengan goroutine user<br/>memakai sekitar 25% CPU"] C --> D["Mark Termination<br/>STW: mematikan write barrier, menghitung statistik"] D --> E["Sweep konkuren<br/>sesuai kebutuhan, bersifat lazy"] E --> F["Penentuan pemicu ronde berikutnya<br/>dihitung Pacer"] F --> C

Abstraksi tiga warna: - Putih: belum dikunjungi, kemungkinan adalah sampah - Abu-abu: sudah dikunjungi, tapi objek yang direferensinya belum selesai dipindai - Hitam: sudah dikunjungi dan semua referensinya sudah dipindai, pasti hidup

Write barrier: karena kode user dan penandaan berjalan konkuren, ada kemungkinan "objek putih" digantungkan di bawah "objek hitam". Write barrier menjamin modifikasi semacam itu tidak membuat objek yang masih hidup ikut dibuang (hybrid write barrier, Yuasa + Dijkstra, sejak Go 1.8, yang menghilangkan STW untuk memindai ulang stack).

4.2 Kapan GC Dipicu: Pacer

Pacer adalah sebuah pengontrol umpan balik, targetnya: saat GC berikutnya selesai, ukuran heap kira-kira 1 + GOGC/100 kali ukuran saat ini.

flowchart LR H["Heap hidup saat ini H_m"] --> T["Target heap = H_m dikali (1 + GOGC/100)"] A["Laju alokasi"] --> P["Pacer memperkirakan<br/>kapan target tercapai"] P --> G["Memicu GC<br/>dan menentukan porsi CPU untuk mark konkuren"] T --> P G --> F["Koreksi umpan balik<br/>memperbaiki estimasi ronde berikutnya"] F --> P

// Versi buruk: setiap permintaan mengalokasi banyak objek sementara

4.4 Empat Senjata untuk Menurunkan Beban GC (urut berdasarkan prioritas)

flowchart TD P["Beban GC tinggi"] --> A1["1. Sedikit alokasi<br/>pre-alokasi kapasitas · pakai ulang buffer · hindari boxing"] P --> A2["2. Pakai ulang<br/>sync.Pool (hati-hati, GC mengosongkannya)"] P --> A3["3. Perkecil objek<br/>tata letak rapat · tipe dengan sedikit pointer lebih cepat dipindai"] P --> A4["4. Setel parameter<br/>GOGC / GOMEMLIMIT (hanya mengobati gejala)"] A1 --> M["Ukur: allocs/op dan GC persen"] A2 --> M A3 --> M A4 --> M M --> D{"Memenuhi target?"} D -- Tidak --> A1 D -- Ya --> E["Tulis ke baseline benchmark"]

Kenyataan tentang sync.Pool: - Ia bukan "obat mujarab untuk semua object pool". Setiap kali GC terjadi, objek di dalam pool dipindah ke victim cache, dan baru dibebaskan benar-benar pada GC berikutnya (ini by design: supaya GC tetap bisa mengklaimnya kembali, sekaligus menghindari semuanya dialokasi ulang tepat setelah GC selesai). Jadi jangan berharap objek yang masuk ke Pool bisa hidup lama. - Ia dipecah per P, sehingga get/put biasanya tanpa lock. - Cocok untuk: buffer besar, encoder sementara, struct besar. Tidak cocok untuk: objek kecil (alokasinya sendiri sudah murah), koneksi yang punya state (lebih jelas kalau Anda yang mengatur siklus hidupnya sendiri). - Wajib dipanggil Reset(), kalau tidak akan bocor data (data permintaan sebelumnya terbawa ke permintaan berikutnya — ini sumber insiden keamanan yang nyata).

6.1 Inlining

Inlining = menempelkan langsung badan fungsi yang dipanggil ke titik pemanggilannya, sehingga biaya pemanggilan dihilangkan, dan membuka optimisasi lintas fungsi lebih lanjut (escape analysis, constant propagation, dan sebagainya).

Inlining di Go berbasis "anggaran biaya" (setiap node AST punya cost, anggaran default-nya 80).

go build -gcflags="-m=2" ./... 2>&1 | grep -E "inline"
go build -gcflags="-l" ./...          # menonaktifkan inlining sepenuhnya (untuk perbandingan)
go build -gcflags="-l -l" ./...       # penonaktifan lebih kuat (mencegah inlining di package ini)

Contoh output:

./main.go:10:6: can inline add with cost 4 as: func(int, int) int { return a + b }
./main.go:18:14: inlining call to add

Situasi umum yang tidak bisa di-inline:

Situasi Alasan
Badan fungsi berisi select / go / defer (dan for pada sebagian versi) Batasan bahasa/compiler; patokan yang benar adalah output -m=2 pada versi Go yang Anda pakai, jangan mengandalkan ingatan
Fungsi rekursif Tidak bisa dibuka
Badan fungsi terlalu besar (melebihi anggaran 80) Model biaya
//go:noinline Dilarang secara eksplisit
Mengandung aliran kontrol kompleks seperti recover Batasan implementasi

Saran praktis: - Jangan memecah fungsi demi inlining — biarkan keterbacaan yang menentukan, dan biarkan compiler yang memutuskan. - Untuk fungsi kecil di hot path yang benar-benar butuh inlining, konfirmasi dengan -m=2; kalau tidak di-inline, cek apakah anggarannya kelewatan. - Parameter debug seperti -gcflags="-d=pctab=pctospadj" hanya dipakai saat menyelidiki bug compiler.

Eksperimen: Efek Rantai Inlining terhadap Escape

func consume(p *T) { ... }        // tidak di-inline → mengoper pointer membuatnya escape
func consumeInlinedCost(p *T) { _ = p.X }  // cukup kecil untuk di-inline → mungkin tidak escape

Kesimpulannya: inlining membuat escape analysis melihat lebih banyak konteks, sehingga mengurangi escape. Ini salah satu alasan tersembunyi kenapa "fungsi kecil itu lebih cepat".

6.2 Bounds Check Elimination (BCE)

Setiap kali Anda menulis s[i], Go akan memeriksa 0 <= i < len(s), dan panic kalau gagal. Inilah sumber keamanan memori di Go, tapi ada biayanya. Compiler akan memakai SSA prove pass untuk menyimpulkan situasi yang "pasti aman" dan menghilangkan pemeriksaannya.

// Versi A: setiap akses diperiksa
func SumA(s []int64) int64 {
    var t int64
    for i := 0; i < len(s); i++ { t += s[i] }   // kondisi loop sudah membuktikan i < len(s) → biasanya bisa dihilangkan
    return t
}

// Versi B: membangun invarian lebih awal untuk membantu compiler membuktikannya
func SumB(s []int64) int64 {
    if len(s) == 0 { return 0 }
    _ = s[len(s)-1]        // kuncinya: buktikan dulu bahwa len(s)-1 itu sah
    var t int64
    for i := 0; i < len(s); i++ { t += s[i] }
    return t
}

Cara memverifikasi:

# Lihat apakah di assembly ada panggilan panicBounds / panicIndex
go build -gcflags="-S" ./... 2>&1 | grep -E "panicBounds|panicIndex"

# Menyalakan output debug prove pass (opsional, eksperimental)
go build -gcflags="-d=ssa/prove/debug=2" ./...

Cara verifikasi yang lebih bisa diandalkan adalah benchmark: manfaat BCE biasanya 5–20%, dan hanya terasa di loop yang ketat. Kalau hasil benchmark tidak berubah, berarti optimisasi ini tidak layak dilakukan — tulis saja dengan jelas "sudah diukur, tidak ada gunanya", karena itu sendiri sudah merupakan keluaran yang berharga.

7.1 Arti dari tiga huruf tersebut

Singkatan Kepanjangan Hakikatnya Jumlahnya
G Goroutine Korutin di user space, berisi stack, status, dan konteks Bisa ribuan hingga puluhan ribu

Satu kalimat untuk mengingatnya: G adalah pekerjaan yang harus diselesaikan, M adalah orang yang mengerjakannya, P adalah stasiun kerja. Tanpa stasiun kerja (P), pekerjaan tidak bisa dilakukan, sebanyak apa pun orangnya (M).

7.2 Kapan penjadwalan terjadi

stateDiagram-v2 [*] --> _Grunnable: go f() _Grunnable --> _Grunning: dipilih oleh P _Grunning --> _Grunnable: kuota waktu habis / di-preempt / Gosched _Grunning --> _Gwaiting: channel memblokir / lock / syscall / IO _Gwaiting --> _Grunnable: peristiwa sudah siap _Grunning --> _Gsyscall: system call _Gsyscall --> _Grunnable: system call kembali<br/>(P mungkin sudah diambil alih) _Grunning --> _Gdead: fungsi kembali _Gdead --> [*]

Poin-poin penting:

  1. Campuran kooperatif dan preemptif. Sejak Go 1.14 mendukung preemption asinkron (preemption berbasis sinyal), yang menyelesaikan masalah lama: "loop for mati yang tidak memanggil fungsi bisa membuat satu P macet total".
  2. Saat syscall memblokir, P akan dilepas dan diserahkan ke M lain agar G lain tetap berjalan. Jadi syscall yang memblokir tidak akan menghabiskan seluruh thread pool.
  3. I/O jaringan lewat netpoller (epoll di Linux): goroutine ditangguhkan tapi tidak memakan M. Inilah inti mengapa Go sanggup menangani C10K.
  4. GOMAXPROCS bukanlah batas atas jumlah core CPU; ia menentukan "berapa banyak P yang boleh menjalankan kode Go secara bersamaan". Di dalam container sebaiknya pakai go.uber.org/automaxprocs agar peka terhadap cgroup limit.

8.2 Semantik channel (harus dikuasai dengan presisi)

Operasi channel nil channel sudah ditutup buffer penuh buffer kosong
kirim ch <- v memblokir selamanya panic memblokir (atau select mengambil default) berhasil
terima <-ch memblokir selamanya langsung mengembalikan nilai nol + ok=false berhasil memblokir
close(ch) panic panic(menutup dua kali) boleh ditutup boleh ditutup

Tiga aturan besi: 1. Tutuplah channel oleh pihak pengirim, jangan oleh pihak penerima (kalau tidak, beberapa pengirim akan panic) 2. Jangan menutup channel yang memiliki lebih dari satu pengirim, kecuali ada koordinasi tambahan 3. select dengan default itu non-blokir; baru dengan time.After / context.Done() ia menjadi ber-timeout

// ✅ Benar: satu pengirim yang menutup
func producer(n int) <-chan int {
    ch := make(chan int)
    go func() {
        defer close(ch)
        for i := 0; i < n; i++ { ch <- i }
    }()
    return ch
}

// ✅ Menggabungkan beberapa worker: koordinasikan dengan WaitGroup lalu tutup
func merge(inputs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, in := range inputs {
        wg.Add(1)
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c { out <- v }
        }(in)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

8.3 Model memori Go: happens-before

Jangan menghafal istilah "model memori"; ingatlah jaminan-jaminan konkret berikut:

Jaminan Penjelasan
Penulisan sebelum go f() terlihat oleh pembacaan di dalam f pembuatan goroutine membangun happens-before
Pengiriman channel happens-before selesainya penerimaan yang bersangkutan ini jaminan inti dari channel
close(ch) happens-before penerima menerima nilai nol
channel tanpa buffer: penerimaan happens-before selesainya pengiriman sinkronisasi dua arah
channel ber-buffer: penerimaan ke-k happens-before pengiriman ke-(k+C) sinkronisasi bergaya semaphore
Mutex.Unlock happens-before Lock berikutnya
WaitGroup.Done happens-before kembalinya Wait
Operasi sync/atomic bersifat sequentially consistent semua goroutine melihat urutan yang sama

Tidak ada jaminan = data race = perilaku tak terdefinisi. Sekalipun "kelihatannya jalan" di x86, bisa saja hancur di ARM atau setelah dioptimasi compiler.

// ❌ Data race yang khas
var done bool
go func() { /* kerja */; done = true }()
for !done { }        // compiler bisa memindahkan done ke luar register → loop mati

// ✅ Pakai channel
done := make(chan struct{})
go func() { defer close(done); /* kerja */ }()
<-done

// ✅ Atau atomic
var done atomic.Bool
go func() { done.Store(true) }()
for !done.Load() { runtime.Gosched() }

9.3 Kerangka referensi

type Pool struct {
    tasks   chan Envelope  // berbatas
    workers int
    wg      sync.WaitGroup

    mu      sync.RWMutex
    state   state   // running / draining / stopped
    stats   Stats

    // dipakai untuk menunggu di Shutdown
    done    chan struct{}
    closeOnce sync.Once
}

type Envelope struct {
    ctx  context.Context
    fn   func(context.Context) error
    errCh chan error   // opsional: agar Submit bisa menunggu hasil
}

func (p *Pool) worker(id int) {
    defer p.wg.Done()
    for {
        select {
        case <-p.done:
            return
        case env, ok := <-p.tasks:
            if !ok { return }
            p.stats.running.Add(1)
            err := p.runSafely(env)     // di dalamnya ada recover
            p.stats.running.Add(-1)
            if err != nil { p.stats.failed.Add(1) } else { p.stats.completed.Add(1) }
            if env.errCh != nil { env.errCh <- err }
        }
    }
}

func (p *Pool) runSafely(env Envelope) (err error) {
    defer func() {
        if r := recover(); r != nil {
            stack := debug.Stack()
            err = fmt.Errorf("task panicked: %v\n%s", r, stack)
        }
    }()
    return env.fn(env.ctx)
}

Beberapa jebakan yang pasti Anda injak, dijelaskan di awal:

  1. Jangan pakai close(tasks) untuk menghentikan produser yang masih mengirim —— itu akan panic. Cara yang benar: channel done + pemeriksaan state.
  2. Jangan memanggil wg.Wait() langsung di dalam Shutdown tanpa timeout —— satu task yang macet bisa membuat layanan tidak pernah keluar. Pakai context.WithTimeout.
  3. Submit setelah shutdown harus mengembalikan error yang jelas(misalnya ErrPoolClosed), tidak boleh membuangnya diam-diam.
  4. recover hanya bermakna di pintu masuk goroutine; recover di dalam fungsi yang dipanggil tidak bisa menangkap panic milik orang lain.
  5. errCh harus ber-buffer 1, kalau tidak worker bisa memblokir selamanya saat mengirim.

10.1 Program Go Anda dilihat dari kacamata kernel

Daftar faktanya:

  • Program Go biasanya berupa satu proses + beberapa thread(clone dari NPTL).
  • goroutine bukanlah thread, kernel tidak bisa melihatnya. Yang dijadwalkan kernel adalah M(thread OS).
  • Setiap proses punya tabel file descriptor sendiri. fd adalah int yang menunjuk ke struktur file di kernel.
  • syscall adalah perpindahan dari user mode ke kernel mode, ada biayanya(orde 1-2 mikrodetik, dan makin mahal setelah mitigasi Spectre/Meltdown).

10.4 Sinyal dan keluar dengan anggun

func main() {
    ctx, stop := signal.NotifyContext(
        context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    srv := &http.Server{Addr: ":8080", Handler: mux}
    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Printf("server error: %v", err)
        }
    }()

    <-ctx.Done()      // menerima SIGINT/SIGTERM
    log.Println("shutting down...")

    shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Printf("forced shutdown: %v", err)
        srv.Close()
    }
    log.Println("bye")
}

Poin-poin penting soal sinyal: - SIGTERM = mohon keluar dengan anggun; SIGKILL = tidak bisa ditangkap, langsung membunuh(di K8s, inilah yang terjadi setelah terminationGracePeriodSeconds) - SIGINT = Ctrl+C - Secara default program Go yang menerima SIGTERM akan langsung keluar; Anda harus mengambil alih dengan signal.Notify - Di dalam container, PID 1 punya perilaku penanganan sinyal yang khusus —— pakai tini atau --init

10.5 Jalur I/O: mengapa write() kembali sukses belum berarti data sudah sampai ke disk

flowchart LR A["app: write()"] --> B["Page cache kernel<br/>write kembali sukses ✅"] B --> C["Thread writeback kernel<br/>dirty page jatuh tempo/melewati ambang"] C --> D["Antrean perangkat blok / penjadwal I/O"] D --> E["Cache controller disk<br/>(mungkin dilindungi baterai/kapasitor)"] E --> F["Media fisik"] B -. Perbedaan kuncinya:

Pemanggilan Jaminannya
write() data berada di page cache kernel; kalau proses crash, data masih ada(kernel akan terus melakukan writeback), tapi kalau listrik mesin putus bisa hilang
fsync() data + metadata sudah sampai ke disk(atau cache disk, tergantung perangkat kerasnya); tidak hilang saat listrik putus(dengan asumsi perangkat kerasnya tidak berbohong)
fdatasync() hanya menyiram data, bukan metadata(misalnya mtime); lebih cepat kalau ukuran file tidak berubah
O_SYNC / O_DSYNC setiap write sinkron, sangat lambat
O_DIRECT melewati page cache, butuh alignment; dipakai ketika database mengelola cache-nya sendiri

Pernyataan yang jujur: sekalipun Anda memanggil fsync, durability tetap bergantung pada filesystem(mode data=ordered/writeback di ext4/xfs), opsi mount(barrier), serta apakah firmware disk Anda jujur. Jangan mengklaim "tahan terhadap pemadaman listrik" kecuali Anda benar-benar sudah melakukan uji cabut kabel daya. Uji yang hanya berupa "kill -9 proses lalu restart" hanya membuktikan "tahan terhadap crash proses".

11.2 Byte stream vs pesan: konsep terpenting minggu ini

  1. Satu kali Write tidak dijamin berkorespondensi dengan satu kali Read. Bisa digabung (Nagle / buffering), bisa juga dipecah (MSS / congestion window / receive buffer).

Terstruktur swadeskripsi TLV / Protobuf / MsgPack Mudah dikembangkan, lintas bahasa Implementasinya rumit

11.3 Eksperimen 1: TCP echo server minimal

func main() {
    ln, err := net.Listen("tcp", "127.0.0.1:8080")
    if err != nil { log.Fatal(err) }
    defer ln.Close()

    for {
        conn, err := ln.Accept()
        if err != nil {
            if errors.Is(err, net.ErrClosed) { return }
            log.Printf("accept: %v", err)
            continue    // error sementara: jangan keluar dari loop
        }
        go handle(conn)
    }
}

func handle(conn net.Conn) {
    defer conn.Close()
    buf := make([]byte, 4096)
    for {
        // Kunci: setiap operasi harus punya deadline; kalau tidak, Anda akan
        // macet selamanya saat peer tidak menutup koneksi
        if err := conn.SetReadDeadline(time.Now().Add(30 * time.Second)); err != nil {
            return
        }
        n, err := conn.Read(buf)
        if err != nil {
            if errors.Is(err, io.EOF) { return }
            var ne net.Error
            if errors.As(err, &ne) && ne.Timeout() { return }
            log.Printf("read: %v", err)
            return
        }
        if _, err := conn.Write(buf[:n]); err != nil { return }
    }
}

Opsi socket yang wajib disetel:

if tc, ok := conn.(*net.TCPConn); ok {
    tc.SetNoDelay(true)                     // matikan Nagle: paket kecil langsung dikirim (skenario latensi rendah)
    tc.SetKeepAlive(true)                   // deteksi koneksi mati
    tc.SetKeepAlivePeriod(30 * time.Second) // tapi hati-hati: default Linux 2 jam, wajib disetel eksplisit
    tc.SetLinger(0)                         // kirim RST saat close (hati-hati: bisa kehilangan data)
}

11.5 UDP dan DNS (poin penting, tidak digali dalam-dalam)

  • UDP tanpa koneksi, tanpa retransmisi, tanpa urutan, tapi punya batas pesan (satu kali WriteTo = satu datagram).
  • Bisa terjadi fragmentasi: jika melebihi MTU (biasanya 1500B, payload sekitar 1472B) akan dipecah oleh lapisan IP; jika satu saja fragmen hilang, seluruh datagram gugur. Karena itu payload UDP sebaiknya ≤ 1200B.
  • Di Go, net.ResolveIPAddr / resolver bawaan akan melakukan kueri DNS; Anda bisa memaksa resolver Go murni dengan GODEBUG=netdns=go, atau memakai resolver sistem dengan netdns=cgo.
  • Cache DNS: resolver Go murni tidak melakukan caching (setiap kali selalu melakukan kueri). Untuk skenario frekuensi tinggi, Anda harus menambahkan cache sendiri atau memakai pustaka semacam dnscache.

12.2 Connection pool sisi klien (http.Transport)

tr := &http.Transport{
    Proxy:                 http.ProxyFromEnvironment,
    DialContext: (&net.Dialer{
        Timeout:   5 * time.Second,     // pembentukan koneksi
        KeepAlive: 30 * time.Second,    // TCP keep-alive
    }).DialContext,

    MaxIdleConns:          100,          // batas atas total koneksi menganggur
    MaxIdleConnsPerHost:   10,           // ⚠️ default-nya hanya 2! wajib diperbesar
    MaxConnsPerHost:       100,          // batas atas koneksi konkuren (termasuk yang aktif)
    IdleConnTimeout:       90 * time.Second,
    TLSHandshakeTimeout:   5 * time.Second,
    ExpectContinueTimeout: 1 * time.Second,
    ForceAttemptHTTP2:     true,
}
client := &http.Client{
    Transport: tr,
    Timeout:   10 * time.Second,   // timeout keseluruhan (termasuk membaca body)
    CheckRedirect: func(req *http.Request, via []*http.Request) error {
        if len(via) >= 5 { return errors.New("too many redirects") }
        return nil
    },
}

Jebakan yang wajib Anda tahu: - Default MaxIdleConnsPerHost adalah 2. Di bawah konkurensi tinggi ini akan menyebabkan koneksi dibuat dan dihancurkan berulang-ulang (TIME_WAIT melonjak, latensi naik). Ini masalah performa klien HTTP Go yang paling umum. - http.Client harus dipakai ulang, jangan membuat yang baru setiap request (kalau tidak, connection pool-nya sia-sia). - Body respons wajib dibaca sampai habis lalu di-Close, jika tidak koneksi tidak bisa dipakai ulang (dan akan bocor).

resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()
// kalau ingin koneksi dipakai ulang, body harus dibaca sampai habis

13.3 Alur pemrosesan (sudut pandang state machine)

Prinsip inti:

  1. Error protokol harus memutus koneksi. Karena aliran byte sudah bergeser dan sinkronisasi tidak bisa dipulihkan; terus membaca sama saja dengan berjudi.
  2. Error bisnis tidak memutus koneksi (mis. NOT_FOUND) — kembalikan kode error dan terus melayani.
  3. Wajib membaca dalam loop sampai jumlah byte yang dibutuhkan terpenuhi. Gunakan io.ReadFull.

13.4 Kerangka kode utama

const (
    magic         = 0x9B
    version       = 0x01
    headerSize    = 8
    crcSize       = 4
    maxPayloadLen = 1 << 20   // 1MB
)

type Frame struct {
    Type    uint8
    Flags   uint8
    Payload []byte
}

// ReadFrame membaca satu frame dari conn. Mengembalikan io.EOF berarti
// peer menutup koneksi dengan bersih.
func ReadFrame(r io.Reader, buf *bufio.Reader) (Frame, error) {
    var hdr [headerSize]byte
    if _, err := io.ReadFull(buf, hdr[:]); err != nil {
        return Frame{}, err       // io.EOF / io.ErrUnexpectedEOF
    }
    if hdr[0] != magic {
        return Frame{}, fmt.Errorf("%w: bad magic 0x%02x", ErrProtocol, hdr[0])
    }
    if hdr[1] != version {
        return Frame{}, fmt.Errorf("%w: unsupported version %d", ErrProtocol, hdr[1])
    }
    length := binary.BigEndian.Uint32(hdr[4:8])
    if length > maxPayloadLen {
        return Frame{}, fmt.Errorf("%w: payload too large: %d", ErrProtocol, length)
    }

    payload := make([]byte, int(length)+crcSize)   // baca payload+crc sekaligus, hemat satu syscall
    if _, err := io.ReadFull(buf, payload); err != nil {
        return Frame{}, err
    }

    // Pemeriksaan: mencakup semua byte header + payload (tidak termasuk crc)
    sum := crc32.ChecksumIEEE(hdr[:])
    sum = crc32.Update(sum, crc32.IEEETable, payload[:length])
    want := binary.BigEndian.Uint32(payload[length:])
    if sum != want {
        return Frame{}, fmt.Errorf("%w: crc mismatch: got %08x want %08x",
            ErrProtocol, want, sum)
    }
    return Frame{Type: hdr[2], Flags: hdr[3], Payload: payload[:length]}, nil
}

Penjelasan poin-poin penting:

  • io.ReadFull akan memanggil Read berulang kali sampai penuh atau terjadi error — inilah cara standar menangani "partial read".
  • Bungkus conn dengan bufio.Reader untuk mengurangi jumlah syscall secara drastis (setiap Read adalah satu syscall).
  • Batasi length sebelum membaca payload; kalau tidak, satu length palsu 4GB bisa membuat servis OOM.
  • Pemeriksaan CRC diletakkan di lapisan aplikasi, bukan untuk mencegah kesalahan jaringan (TCP sudah menangani itu), melainkan untuk menangkap bug implementasi kita sendiri (serialisasi/deserialisasi yang bergeser).

14.2 Append-only log: primitif persistensi yang paling sederhana

Mengapa append-only begitu populer?

flowchart LR subgraph RND["Tulis acak (update di tempat / in-place)"] R1["seek ke posisi"] R2["baca blok lama"] R3["ubah di memori"] R4["tulis kembali"] R5["bisa melintasi blok / tulis sebagian"] R1 --> R2 --> R3 --> R4 --> R5 end subgraph APP["Tulis append (append-only)"] A1["Posisikan ke akhir file (offset sudah diketahui)"] A2["Tulis berurutan"] A3["Tidak perlu membaca data lama"] A1 --> A2 --> A3 end
  • Tulis berurutan di HDD 1~2 orde magnitudo lebih cepat daripada tulis acak (menghemat seek); di SSD juga lebih cepat (mengurangi write amplification dan tekanan GC)
  • Aman terhadap crash: tulis append tidak akan merusak data yang sudah ada; skenario terburuk hanyalah satu record yang tidak lengkap di ekor → cukup dibuang dengan checksum
  • Inilah sebabnya WAL, Kafka, dan hampir semua database memakai append-only log

14.3 Desain format record

+--------+--------+--------+--------+
|  crc32 (4B, BE)                  |   ← mencakup length+type+payload
+--------+--------+--------+--------+
|  length (4B, BE)                 |   ← jumlah byte payload
+--------+---+----+--------+--------+
| type(1B)| reserved(3B)           |
+--------+-------------------------+

14.4 Implementasi: append-only log

type Log struct {
    mu     sync.Mutex
    f      *os.File
    buf    *bufio.Writer
    offset int64      // offset logis (jumlah byte yang sudah dipersistenkan)
    syncPolicy SyncPolicy
}

type SyncPolicy int
const (
    SyncNone   SyncPolicy = iota // tanpa fsync: paling cepat, data hilang saat crash
    SyncEvery                    // fsync setiap record: paling lambat, paling aman
    SyncPeriodic                 // berkala / berdasarkan jumlah: kompromi (umum dipakai)
)

func Open(path string, p SyncPolicy) (*Log, error) {
    f, err := os.OpenFile(path, os.O_CREATE|os.O_RDWR|os.O_APPEND, 0o644)
    if err != nil { return nil, err }
    st, err := f.Stat()
    if err != nil { f.Close(); return nil, err }
    return &Log{f: f, buf: bufio.NewWriterSize(f, 64<<10), offset: st.Size(), syncPolicy: p}, nil
}

func (l *Log) Append(recType uint8, payload []byte) (int64, error) {
    l.mu.Lock()
    defer l.mu.Unlock()

    off := l.offset
    var hdr [12]byte
    binary.BigEndian.PutUint32(hdr[0:4], uint32(len(payload)))
    hdr[4] = recType

    // CRC mencakup length + type + reserved + payload
    sum := crc32.ChecksumIEEE(hdr[0:12])
    sum = crc32.Update(sum, crc32.IEEETable, payload)

    var crc [4]byte
    binary.BigEndian.PutUint32(crc[:], sum)

    if _, err := l.buf.Write(crc[:]); err != nil { return 0, err }
    if _, err := l.buf.Write(hdr[:]); err != nil { return 0, err }
    if _, err := l.buf.Write(payload); err != nil { return 0, err }

    l.offset += int64(4 + 12 + len(payload))

    if l.syncPolicy == SyncEvery {
        if err := l.sync(); err != nil { return 0, err }
    }
    return off, nil
}

func (l *Log) sync() error {
    if err := l.buf.Flush(); err != nil { return err }   // wajib Flush ke kernel dulu
    return l.f.Sync()                                    // barulah fsync
}

Urutan kritis (kalau salah urutan, data hilang):

1. buf.Flush()  → buffer user space → page cache kernel
2. f.Sync()     → page cache → disk

Kalau hanya memanggil Sync() tanpa Flush(), data masih berada di dalam bufio Anda, dan fsync tidak menyiram apa pun.

14.5 Recovery: memindai log untuk membangun ulang state

func (l *Log) Replay(fn func(off int64, recType uint8, payload []byte) error) error {
    // Buka ulang dalam mode read-only (hindari tercampur dengan Append sehingga offset kacau)
    f, err := os.Open(l.path)
    if err != nil { return err }
    defer f.Close()

    r := bufio.NewReaderSize(f, 64<<10)
    var off int64
    for {
        var crc [4]byte
        if _, err := io.ReadFull(r, crc[:]); err != nil {
            if errors.Is(err, io.EOF) { return nil }        // berakhir bersih
            if errors.Is(err, io.ErrUnexpectedEOF) {        // record setengah jadi di ekor
                return l.truncateTo(off)                    // buang saja
            }
            return err
        }
        var hdr [12]byte
        if _, err := io.ReadFull(r, hdr[:]); err != nil { return l.truncateTo(off) }

        length := binary.BigEndian.Uint32(hdr[0:4])
        if length > maxRecordSize { return l.truncateTo(off) }   // jelas-jelas rusak

        payload := make([]byte, length)
        if _, err := io.ReadFull(r, payload); err != nil { return l.truncateTo(off) }

        // Verifikasi
        sum := crc32.ChecksumIEEE(hdr[:])
        sum = crc32.Update(sum, crc32.IEEETable, payload)
        if binary.BigEndian.Uint32(crc[:]) != sum {
            return l.truncateTo(off)     // mulai dari sini tidak bisa dipercaya
        }

        if err := fn(off, hdr[4], payload); err != nil { return err }
        off += int64(4 + 12 + int(length))
    }
}

Strategi recovery: - Menemukan error CRC / panjang yang tidak wajar / record setengah jadi → potong file mulai offset tersebut(f.Truncate(off)), buang semua isi setelahnya - Inilah keuntungan terbesar append-only: kerusakan hanya mungkin terjadi di ekor

Minggu 16 · B-tree, LSM, Indeks, Transaksi, dan Isolation

16.1 Seperti apa bentuk B-tree

flowchart TD R["Node akar<br/>keys: [50, 100]"] R --> A["Node anak<br/>keys: [10, 20, 30]"] R --> B["Node anak<br/>keys: [60, 70, 80]"] R --> C["Node anak<br/>keys: [110, 120]"] A --> A1["Daun<br/>10→v, 20→v, 30→v"] A --> A2["Daun<br/>..."] B --> B1["Daun<br/>60→v ..."] C --> C1["Daun<br/>110→v, 120→v"] A1 -. "linked list dua arah" .-> A2 A2 -.-> B1

Sifat-sifat kunci:

  • Seimbang: semua daun berada di level yang sama, kompleksitas pencarian O(log_B N), dengan B adalah orde (berapa banyak key yang bisa muat dalam satu node)
  • Fan-out tinggi: satu node biasanya = satu halaman disk (4KB/16KB), bisa memuat ratusan key → cukup 3~4 level untuk mengindeks ratusan juta baris
  • Linked list pada daun: mendukung range scan yang efisien (range scan di LSM harus menggabungkan beberapa level, lebih merepotkan)
  • Update in-place: perubahan harus ditulis kembali ke halaman asalnya → tulis acak, inilah sebabnya ia lebih lambat menulis dibanding LSM

16.2 B-tree vs LSM: menjelaskan trade-off-nya dengan jelas

Dimensi B-tree LSM-tree
Tulis Tulis acak + WAL, amplifikasi tulis tinggi Tulis berurutan, throughput tulis tinggi
Baca (point lookup) Stabil O(log N), sekitar 3~4 kali I/O Bisa memeriksa beberapa level, dimitigasi dengan BloomFilter
Range scan Sangat baik (linked list daun) Biasa saja (penggabungan multi-level)
Amplifikasi ruang Rendah (tapi ada fragmentasi / fill factor) Tinggi (banyak versi hidup berdampingan)
Amplifikasi tulis Sedang (penulisan ulang level halaman) Tinggi (compaction)
Rasio kompresi Biasa saja Baik (SSTable ringkas)
Representasi tipikal PostgreSQL, MySQL InnoDB, SQLite RocksDB, Cassandra, ClickHouse, TiDB

Inilah sebabnya PostgreSQL memakai B-tree, sementara TiDB/CockroachDB di bawahnya memakai RocksDB: yang pertama mengoptimalkan baca transaksional, yang terakhir mengoptimalkan throughput tulis dan skalabilitas horizontal.

16.5 Eksperimen mini: menambahkan transaksi single-key "read committed" ke gostore

Jangan serakah soal cakupan. Implementasikan antarmuka transaksi yang minimal:

type Tx interface {
    Get(key []byte) ([]byte, bool)
    Put(key, value []byte)
    Delete(key []byte)
    Commit() error
    Rollback() error
}

Strategi (tulis ke dalam ADR): - Operasi tulis disangga dulu secara lokal di dalam transaksi - Saat Commit, sekali saja menambahkan satu record TXN_COMMIT (berisi semua operasi) ke WAL → atomicitas dijamin oleh "penulisan satu record tunggal" - Ini adalah atomic commit yang paling sederhana: batch append + satu CRC; kalau sukses semuanya berlaku, kalau gagal semuanya dibuang

Keterbatasan desain ini (harus ditulis dengan jelas): tidak mendukung deteksi konflik tulis antar-transaksi secara konkuren (tanpa MVCC/lock); hanya menjamin atomicitas dalam satu transaksi.

Implementasi retry yang benar:

type RetryConfig struct {
    MaxAttempts    int
    InitialBackoff time.Duration
    MaxBackoff     time.Duration
    Multiplier     float64
    Jitter         bool
    Budget         *RetryBudget   // anggaran retry global (penting!)
}

func Do(ctx context.Context, cfg RetryConfig, fn func(context.Context) error) error {
    var lastErr error
    backoff := cfg.InitialBackoff
    for attempt := 0; attempt < cfg.MaxAttempts; attempt++ {
        if err := ctx.Err(); err != nil { return err }   // deadline sudah habis, jangan retry lagi

        if attempt > 0 {
            if cfg.Budget != nil && !cfg.Budget.TryConsume() {
                return fmt.Errorf("retry budget exhausted: %w", lastErr)
            }
            d := backoff
            if cfg.Jitter { d = jitter(backoff) }        // tambah jitter agar retry tidak sinkron
            select {
            case <-time.After(d):
            case <-ctx.Done():
                return ctx.Err()
            }
            backoff = min(time.Duration(float64(backoff)*cfg.Multiplier), cfg.MaxBackoff)
        }

        lastErr = fn(ctx)
        if lastErr == nil { return nil }
        if !isRetryable(lastErr) { return lastErr }      // 4xx jangan di-retry
    }
    return fmt.Errorf("after %d attempts: %w", cfg.MaxAttempts, lastErr)
}

// full jitter: acak di [0, backoff), paling efektif untuk memecah retry yang serentak
func jitter(d time.Duration) time.Duration {
    return time.Duration(rand.Int64N(int64(d)))
}

Daftar aturan retry:

Aturan Penjelasan
Hanya retry error yang bisa di-retry connection error, timeout, 503, 429; 400/401/404 jangan di-retry
Harus menghormati deadline berhenti begitu ctx.Err() tidak nil
Exponential backoff + jitter tanpa jitter akan terjadi "retry tersinkronisasi" (thundering herd)
Anggaran retry jumlah retry global tidak lebih dari 10~20% traffic normal
Retry hanya operasi yang idempoten atau jadikan idempoten terlebih dahulu
Hormati header Retry-After server memberi tahu secara eksplisit berapa lama harus menunggu
Gabungkan dengan circuit breaker kalau gagal terus-menerus, gagalkan cepat, jangan retry terus

func (s *Service) Transfer(ctx context.Context, idemKey string, req TransferReq) (*Result, error) {
    // Harus dalam satu transaksi: cek catatan idempotency + tulis data bisnis + tulis catatan idempotency
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil { return nil, err }
    defer tx.Rollback()

    // 1. Cek dulu apakah sudah pernah diproses (pakai SELECT ... FOR UPDATE atau deteksi konflik unique index)
    var prev Result
    if err := tx.GetContext(ctx, &prev,
        `SELECT result FROM idempotency WHERE key = $1`, idemKey); err == nil {
        return &prev, nil       // sudah diproses, langsung kembalikan
    }

    // 2. Jalankan logika bisnis
    if err := s.doTransfer(ctx, tx, req); err != nil { return nil, err }
    res := Result{OK: true}

    // 3. Catat hasil idempotency (ada unique index pada key; saat konkuren, konflik menjamin hanya satu yang sukses)
    _, err = tx.ExecContext(ctx,
        `INSERT INTO idempotency (key, result, created_at) VALUES ($1,$2,now())
         ON CONFLICT (key) DO NOTHING`, idemKey, res)
    if err != nil { return nil, err }

    if err := tx.Commit(); err != nil { return nil, err }
    return &res, nil
}

18.2 Matematika kuorum (quorum)

Misalkan ada N replica, tulis butuh W ack, baca butuh meng-query R replica:

  • Kondisi cukup untuk pembacaan konsisten kuat: W + R > N
  • Konfigurasi umum: N=3, W=2, R=2 (3 replica, mentolerir 1 kegagalan)
  • N=3, W=1, R=3: tulis cepat baca lambat (banyak tulis, sedikit baca)
  • N=3, W=3, R=1: tulis lambat baca cepat (banyak baca, sedikit tulis)

18.4 Leader election (Pemilihan Leader)

Mengapa butuh pemilihan leader? Karena banyak penulis perlu sepakat soal "urutan operasi", dan memilih leader adalah cara paling sederhana untuk mencapai konsensus (menyerahkan keputusan urutan kepada satu pihak).

Dua jenis implementasi leader election:

flowchart TD A["Implementasi leader election"] --> B["Service koordinasi eksternal<br/>etcd / ZooKeeper<br/>pakai lease + transaksi"] A --> C["Konsensus bawaan<br/>Raft / Paxos"] B --> B1["Kelebihan: sederhana, sudah teruji"] B --> B2["Kelemahan: tambah satu dependensi<br/>(etcd sendiri juga punya Raft)"] C --> C1["Kelebihan: tanpa dependensi eksternal"] C --> C2["Kelemahan: implementasi rumit, mudah salah"]

Mekanisme lease (sewa):

// Implementasi leader election dengan etcd (disederhanakan)
func campaign(ctx context.Context, cli *clientv3.Client, key, id string) error {
    s, err := concurrency.NewSession(cli, concurrency.WithTTL(10))
    if err != nil { return err }
    e := concurrency.NewElection(s, key)
    if err := e.Campaign(ctx, id); err != nil { return err }   // memblokir sampai menjadi leader

    // Setelah menjadi leader: perpanjang lease berkala + pantau kehilangan leadership
    select {
    case <-s.Done():          // lease kedaluwarsa (proses macet/putus jaringan)
        return ErrLostLeadership
    case <-ctx.Done():
        e.Resign(ctx)
        return ctx.Err()
    }
}

Hal penting: lease kedaluwarsa ≠ saya bukan leader lagi. Bisa saja terjadi "leader lama masih mengira dirinya leader" (jeda GC, partisi jaringan membuat perpanjangan lease gagal). Karena itu:

  • Setiap operasi tulis harus memvalidasi leadership (fence token / epoch)
  • Dari sinilah asal fencing token: nomor yang monotonik naik, dan layer penyimpanan menolak token yang lebih kecil

18.5 Eksperimen: KV primary-replica

Arsitektur:
  Client → Router → Primary (tulis + baca)
                  → Replica1 (hanya baca, replikasi asinkron)
                  → Replica2 (hanya baca, replikasi asinkron)

Implementasi:
  ✅ tulis harus lewat primary
  ✅ primary menulis lokal + meneruskan ke replica (bisa dikonfigurasi sinkron/asinkron/semi-sinkron)
  ✅ baca bisa dikonfigurasi: lewat primary (konsisten kuat) atau replica mana pun (mungkin usang)
  ✅ primary mati: promosikan satu replica secara manual/otomatis (di fase ini boleh manual)

Minggu 19 · Konsensus: Raft

19.1 Mengapa butuh Raft

Replikasi primary-replica dengan sendirinya tidak menyelesaikan:

  • siapa leadernya (leader election)
  • setelah leader mati, bagaimana menjamin tulis yang sudah di-commit tidak hilang
  • saat partisi, bagaimana menghindari split-brain

Tujuan Raft: algoritma konsensus yang bisa dipahami. Ia memecah masalah menjadi tiga sub-masalah:

  1. Leader election (pemilihan leader)
  2. Replikasi log (log replication)
  3. Safety (keamanan: log yang sudah di-commit tidak akan hilang)

19.2 Tiga peran dan term dalam Raft

stateDiagram-v2 [*] --> Follower: mulai Follower --> Candidate: election timeout<br/>(acak 150-300ms) Candidate --> Leader: mendapat suara mayoritas Candidate --> Follower: menerima heartbeat dengan term lebih tinggi<br/>atau election timeout tanpa hasil Candidate --> Candidate: election timeout, mulai term baru dan coba lagi Leader --> Follower: menemukan term lebih tinggi<br/>(setelah partisi jaringan pulih) note right of Leader Leader mengirim heartbeat AppendEntries secara berkala setiap RPC membawa term begitu menerima term lebih tinggi, langsung turun takhta end note

Term (masa jabatan) adalah jam logika:

flowchart LR T1["term 1<br/>leader=A"] --> T2["term 2<br/>sedang pemilihan<br/>tidak ada leader"] T2 --> T3["term 3<br/>leader=B"] T3 --> T4["term 4<br/>leader=A"] T4 --> T5["term 5<br/>leader=B (saat ini)"]
  • Setiap node mempersistenkan currentTerm, votedFor, dan log
  • Menerima permintaan dengan term lebih tinggi → segera perbarui term dan menjadi Follower
  • Satu term paling banyak satu leader (dijamin oleh voting mayoritas)

19.3 Alur pemilihan

sequenceDiagram participant F1 as Node1 (Follower) participant F2 as Node2 participant F3 as Node3 Note over F1: election timeout (acak) → term 2, Candidate F1->>F1: votedFor = self, votes = 1 F1->>F2: RequestVote(term=2, lastLogIndex=7, lastLogTerm=1) F1->>F3: RequestVote(term=2, ...) F2-->>F1: vote granted ✅ F3-->>F1: vote granted ✅ Note over F1: mendapat 3/3 → menjadi Leader F1->>F2: AppendEntries(term=2, heartbeat) F1->>F3: AppendEntries(term=2, heartbeat)

Aturan voting ("paling tidak sama baru dengan saya"): - (lastLogTerm, lastLogIndex) kandidat harus tidak lebih tertinggal dari pemberi suara, kalau tidak maka ditolak - Aturan ini menjamin: leader yang terpilih pasti memuat semua entri log yang sudah di-commit

Pengacakan election timeout bertujuan menghindari banyak node memulai pemilihan bersamaan yang berujung seri berulang.

19.4 Replikasi log

sequenceDiagram participant C as Client participant L as Leader participant F1 as Follower1 participant F2 as Follower2 C->>L: SET x=1 L->>L: tambahkan log (term=5, idx=10) L->>F1: AppendEntries(term=5, prevIdx=9, prevTerm=5, entry) L->>F2: AppendEntries(term=5, prevIdx=9, prevTerm=5, entry) F1-->>L: success F2-->>L: success Note over L: mayoritas sukses → commitIndex=10 L->>L: terapkan ke state machine L-->>C: OK ✅ L->>F1: AppendEntries(commitIndex=10) L->>F2: AppendEntries(commitIndex=10)

Pemeriksaan konsistensi: AppendEntries membawa prevLogIndex dan prevLogTerm. Kalau Follower menemukan ketidakcocokan ia menolak, lalu Leader memundurkan nextIndex dan mencoba lagi. Inilah yang menjamin sifat "kecocokan awalan" pada log.

19.5 Daftar implementasi (berurut dari yang paling mudah)

Fase A (harus selesai minggu ini):
  ✅ state machine node: Follower / Candidate / Leader
  ✅ persistensi: currentTerm, votedFor, log[]
  ✅ election timeout (diacak) + RPC RequestVote
  ✅ heartbeat AppendEntries (entries kosong)
  ✅ penambahan log + pemeriksaan konsistensi + pemunduran nextIndex
  ✅ pemajuan commitIndex + penerapan ke state machine

Fase B (nilai tambah):
  ⬜ kompresi log (snapshot)
  ⬜ perubahan keanggotaan (joint consensus)
  ⬜ ReadIndex / LeaseRead (pembacaan linearizable)
  ⬜ PreVote (mencegah gangguan term setelah partisi pulih)

Poin penting state machine:

type Raft struct {
    mu sync.Mutex

    // Status yang dipersistenkan (setiap perubahan harus ditulis ke disk dulu sebelum merespons)
    currentTerm int
    votedFor    int
    log         []LogEntry   // index mulai dari 1

    // Status yang mudah hilang (volatile)
    commitIndex int
    lastApplied int
    state       State

    // Khusus Leader
    nextIndex  []int
    matchIndex []int

    // Komunikasi
    applyCh chan ApplyMsg
}

6 titik yang paling sering salah ditulis (hindari dari awal):

  1. Urutan persistensi: currentTerm / votedFor harus ditulis ke disk dulu baru membalas RPC
  2. Granularitas lock: di dalam RPC handler jangan memegang lock terus-menerus sambil melakukan I/O (bisa deadlock); pakai salinan data atau kunci tersegmentasi
  3. Pemeriksaan term: setiap handler RPC harus menangani "menerima term lebih tinggi → turun takhta"
  4. Perhitungan commitIndex: hanya boleh pakai median dari matchIndex, dan hanya boleh meng-commit log pada term saat ini (tidak boleh langsung meng-commit log dari term lama, kecuali ada log baru di term saat ini yang berhasil di-commit)
  5. Election timeout harus diacak, dan harus lebih besar dari interval heartbeat (kalau tidak, leader tidak akan pernah terpilih)
  6. apply harus setelah commit, dan harus dilakukan oleh goroutine terpisah secara serial

21.3 Mekanisme inti queue: visibility timeout

sequenceDiagram participant P as Producer participant Q as Queue participant W as Worker P->>Q: enqueue(job) Note over Q: state=READY Q->>W: dequeue(job) → state=INVISIBLE<br/>visibilityTimeout=30s alt worker sukses W->>Q: ack(jobId) Note over Q: job dihapus ✅ else worker crash / timeout Note over Q: setelah 30s kembali menjadi READY Q->>W2: dikirim ulang ke worker lain ⚠️ dieksekusi dua kali Note over W2: karena itu job harus idempoten else jumlah retry melewati batas Q->>DLQ: dipindahkan ke dead-letter queue end

Mengapa butuh visibility timeout? (bukan "hapus begitu diambil")

  • Hapus begitu diambil: worker crash → tugas hilang selamanya
  • Visibility timeout: worker crash → tugas kembali terlihat, diproses worker lain
  • Biayanya: bisa dieksekusi dua kali → karena itu logika konsumsi harus idempoten

Mengimplementasikan queue dengan database (cara yang paling umum di Go, supaya tidak perlu membawa Kafka/RabbitMQ):

-- Ambil satu batch tugas secara atomik (kuncinya: FOR UPDATE SKIP LOCKED)
UPDATE jobs
SET state = 'running',
    visible_until = now() + interval '30 seconds',
    attempts = attempts + 1,
    worker_id = $1
WHERE id IN (
    SELECT id FROM jobs
    WHERE state = 'ready' AND visible_until <= now()
    ORDER BY priority DESC, created_at
    LIMIT $2
    FOR UPDATE SKIP LOCKED      -- kuncinya: lewati baris yang sedang dikunci, banyak worker tidak saling memblokir
)
RETURNING *;

FOR UPDATE SKIP LOCKED adalah intinya: ia membuat banyak worker yang mengambil tugas secara konkuren tidak saling menunggu. Ini teknik standar untuk membuat queue di Postgres.

23.1 Teori antrean: mengapa latensi meledak saat utilisasi > 80%

flowchart LR subgraph L["Beban rendah ρ=0.3"] L1["Antrean hampir kosong<br/>latensi ≈ waktu layanan"] end subgraph M["Beban menengah ρ=0.7"] M1["Antrean kadang terisi<br/>latensi = waktu layanan × 2~3"] end subgraph H["Beban tinggi ρ=0.95"] H1["Antrean sangat panjang<br/>latensi = waktu layanan × 20"] end subgraph O["Overload ρ>1"] O1["Antrean tumbuh tak terbatas<br/>latensi → ∞<br/>sistem praktis tidak berguna"] end

Rumus inti (Little's Law):

L = λ × W
Panjang antrean = laju kedatangan × waktu tinggal rata-rata

Serta waktu tunggu M/M/1: W = 1 / (μ - λ), dengan μ adalah laju layanan dan λ adalah laju kedatangan. Ketika λ → μ, maka W → ∞. Inilah sebabnya kita harus menyisakan ruang cadangan.

Kesimpulan rekayasa: - Utilisasi target biasanya 60~70% (bukan 95%) - Harus ada rate limiting, kalau tidak saat λ > μ sistem akan kolaps, bukan sekadar melambat - Amplifikasi tail latency: satu permintaan fan-out ke 100 node, masing-masing P99 = 100ms, maka P99 keseluruhan akan sangat buruk (peluang ada satu yang lambat sangat tinggi)

24.1 ADR: seperti apa yang bisa disebut berguna

# ADR-0007: Memakai rate limiting token bucket, bukan fixed window counter

## Status
Accepted (2026-XX-XX) · menggantikan ADR-0003

## Konteks
Service pemesanan mengalami kenaikan P99 dari 200ms ke 3.2s saat puncak promo, dan muncul OOM.
Load test menunjukkan: saat konkurensi > 800, antrean tumbuh tanpa batas (lihat docs/benchmarks/week23).

## Keputusan
Gunakan rate limiting token bucket dari golang.org/x/time/rate di layer API gateway:
- Laju stabil 1000 QPS
- Kapasitas burst 100 (mengizinkan puncak singkat)
- Jika dilampaui, kembalikan 429 + Retry-After

## Opsi alternatif
| Opsi | Kelebihan | Kelemahan | Mengapa ditolak |
| --- | --- | --- | --- |
| Fixed window counter | implementasi sederhana | di batas window bisa meloloskan 2× traffic | lonjakan di batas window tidak bisa diterima |
| Sliding window | presisi | memori O(jumlah permintaan) | overhead memori besar |
| Tanpa rate limiting, andalkan scaling | tidak ada perubahan kode | tidak sanggup menghadapi lonjakan setingkat flash sale; biaya tinggi | load test sudah membuktikan akan OOM |

## Konsekuensi
Positif: P99 stabil di bawah 210ms; OOM hilang.
Negatif: sekitar 0.3% permintaan ditolak (429). Perlu logika retry di sisi klien.
Masih dipantau: apakah kapasitas burst 100 sudah tepat, perlu disesuaikan setelah promo besar berikutnya.

## Cara verifikasi
Setelah `vegeta attack -rate=2000/s -duration=60s`, periksa:
- Proporsi 429 < 1%
- P99 < 250ms
- Memori stabil

Empat elemen wajib ADR: konteks (berisi data), keputusan (konkret), alternatif beserta alasan penolakan, konsekuensi (termasuk yang negatif). ADR tanpa "alasan penolakan" hanya catatan peristiwa sesudahnya, tidak punya nilai sebagai keputusan.

- Kalau karena lonjakan traffic: pastikan rate limiting sudah berjalan; bila perlu scaling sementara
- Kalau karena downstream lambat: pastikan circuit breaker sudah terbuka; aktifkan degradasi (kembalikan cache/nilai default)
- Kalau karena GC: sementara setel `GOGC` (mengobati gejala), lalu turunkan laju alokasi (mengobati akar masalah)
- Kalau karena deadlock/pemblokiran: rollback perubahan terakhir

### Pencegahan
- Load test mencakup tingkat traffic tersebut (saat ini baru diuji sampai 1000 QPS, padahal puncak nyata 2000)
- Tambah alarm kedalaman antrean
- Akar masalah kali ini: ______ (wajib diisi setelah kejadian)

Tulis minimal 5 skenario:

  1. Latensi P99 naik
  2. Rasio error melonjak
  3. Memori terus bertumbuh (dugaan kebocoran)
  4. Jumlah goroutine meledak
  5. Antrean menumpuk dan tidak dikonsumsi
  6. Disk penuh
  7. Replica tertinggal / replikasi terputus
  8. Service dependensi tidak tersedia

Standar Code Review dan Quality Gate

Dokumen ini menyelesaikan separuh lain dari "peningkatan kemampuan teknis": bagaimana membuat output setiap orang di tim mencapai batas bawah yang sama. Seberapa baik pun individu belajar, tanpa standar review dan quality gate otomatis, rata-rata level tim tetap ditentukan oleh commit yang paling asal-asalan.

0. Samakan Dulu Tiga Istilah

Istilah Definisi Contoh
Bug Kode tidak bekerja sesuai maksud penulisnya Kurang satu pengecekan batas
Defect Kode bisa jalan, tapi perilakunya tidak dapat diterima pada kondisi tertentu Antrean tak berbatas menyebabkan OOM
Smell Bukan salah, tapi menaikkan probabilitas error di masa depan Mencampur receiver value/pointer

Tujuan review bukan memusnahkan smell (itu tidak akan ada habisnya diperdebatkan), melainkan memprioritaskan menangkap bug dan defect.

1. Alur Review

flowchart TD A["Penulis mengajukan PR"] --> B["Quality gate otomatis CI<br/>format · vet · lint · test · race · bench"] B -- gagal --> A B -- lolos --> C["Checklist swa-review penulis<br/>(Bagian 3 dokumen ini)dicentang lalu ditempel ke deskripsi PR"] C --> D["Reviewer memeriksa berdasarkan checklist per domain<br/>(Bagian 4 dokumen ini)"] D --> E{"Ada masalah Blocking?"} E -- ya --> F["Tolak, dan **kutip nomor itemnya**"] F --> A E -- tidak --> G{"Ada saran Non-blocking?"} G -- ya --> H["Approve + tinggalkan saran<br/>penulis boleh tindak lanjuti nanti"] G -- tidak --> I["Approve → Merge"]

Tiga Aturan Besi

  1. Penolakan wajib mengutip nomor item(misalnya "melanggar C-3"). Penolakan tanpa nomor akan berubah menjadi debat subjektif.
  2. Saran Non-blocking tidak memblokir merge. Reviewer tidak boleh menjadikan "saya lebih suka cara penulisan lain" sebagai Blocking.
  3. Swa-review penulis mendahului review orang lain. PR tanpa checklist swa-review boleh langsung tidak dilihat oleh reviewer.

2. Definisi Tingkat Keparahan

Level Arti Penanganan
Blocker Menyebabkan kehilangan data, celah keamanan, crash produksi, kebocoran resource Wajib diperbaiki
Major Akan bermasalah di jalur beban tinggi/error; atau jelas melanggar konvensi arsitektur Wajib diperbaiki
Minor Keterbacaan, penamaan, pemeliharaan Disarankan diperbaiki, tidak memblokir
Nit Murni gaya penulisan Opsional, jangan buang waktu di sini

3. Checklist Swa-review Penulis(wajib diisi sebelum mengajukan PR)

### Checklist Swa-review
- [ ] `gofmt` / `goimports` sudah dijalankan
- [ ] `go vet ./...` tidak mengeluarkan output
- [ ] `golangci-lint run` tidak ada peringatan baru
- [ ] Kode yang ditambahkan/diubah punya test, dan mencakup jalur kegagalan
- [ ] `go test -race ./...` lolos(wajib untuk kode konkuren)
- [ ] Perubahan terkait performa menyertakan perbandingan `benchstat` sebelum/sesudah
- [ ] Semua goroutine baru punya jalur keluar
- [ ] Semua resource(fd / conn / ticker / body)di-defer close
- [ ] Semua pemanggilan eksternal punya timeout/pembatalan
- [ ] Penanganan error tidak menelan error(tidak ada `_ = err`)
- [ ] Tidak ada angka ajaib yang di-hardcode(atau sudah diberi komentar yang menjelaskan asalnya)
- [ ] README / dokumentasi sudah diperbarui sinkron
- [ ] Keterbatasan yang diketahui sudah ditulis di dokumentasi

4. Checklist Review(per domain)

A. Ke-benaran Umum(semua kode)

# Item Pemeriksaan Level Masalah Khas
A-1 Apakah error ditangani dengan benar(tidak ditelan, tidak panic mentah-mentah) Blocker _ = doSomething()
A-2 Apakah error membawa konteks(fmt.Errorf("...: %w", err)) Major Informasi rantai pemanggilan hilang
A-3 Kondisi batas: kosong, nilai nol, satu elemen, nilai maksimum Major len(s)-1 pada slice kosong
A-4 Pengecekan nil(pointer, slice, map, interface) Major Menulis ke map nil akan panic
A-5 Overflow integer / pemotongan konversi tipe Major int(uint32) pada 32-bit
A-6 Tidak ada path, port, atau kunci rahasia yang di-hardcode Blocker Kunci rahasia masuk ke repositori
A-7 Tidak ada input pengguna yang langsung disisipkan ke SQL / perintah Blocker SQL injection
A-8 Apakah test benar-benar mengasersi perilaku(bukan sekadar memanggil fungsi sekali) Major Test tidak punya if got != want

B. Konkurensi dan goroutine(sesuai Fase 2)

# Item Pemeriksaan Level Masalah Khas
B-1 Setiap go func() punya jalur keluar yang pasti Blocker for {} tanpa keluar
B-2 Pihak yang menutup channel unik dan jelas Blocker Banyak pihak close → panic
B-3 Apakah select punya cabang ctx.Done() Major Tidak bisa dibatalkan
B-4 Apakah state bersama punya sinkronisasi(lock/atomic/channel) Blocker Data race
B-5 Apakah ada I/O atau pemanggilan fungsi eksternal sambil memegang lock Major Deadlock / scope lock terlalu luas
B-6 Apakah urutan lock konsisten(beberapa lock) Blocker Deadlock AB-BA
B-7 Apakah antrean/worker/connection pool berbatas Major Tak berbatas → OOM
B-8 Apakah ada recover di dalam goroutine(kode pihak ketiga/tidak terkendali) Major Satu panic menjatuhkan proses
B-9 Apakah WaitGroup.Add dipanggil di luar goroutine Blocker Race membuat Wait kembali lebih awal
B-10 Apakah context diteruskan sampai pemanggilan paling bawah Major Hulu sudah batal tapi hilir masih jalan
B-11 Apakah time.After bocor di dalam loop Minor Memakai time.After dalam loop menumpuk timer
B-12 Apakah ada context.Background() di dalam kode library Minor Seharusnya diterima dari pemanggil

C. Jaringan dan Protokol(sesuai Fase 3)

# Item Pemeriksaan Level Masalah Khas
C-1 Setiap koneksi punya read/write deadline Blocker Klien lambat menghabiskan fd
C-2 Loop baca menangani io.EOF / io.ErrUnexpectedEOF / timeout dengan benar Blocker Loop tak berujung / error palsu
C-3 Memakai io.ReadFull untuk framing(bukan sekali Read) Blocker Bug setengah paket
C-4 Panjang pesan punya batas atas, dan divalidasi sebelum alokasi Blocker length palsu → OOM
C-5 Error protokol memutus koneksi, error bisnis tidak Major Terus membaca setelah framing bergeser
C-6 HTTP server lengkap dengan 4 timeout Blocker Slowloris / kebocoran koneksi
C-7 HTTP client memakai ulang Transport, MaxIdleConnsPerHost sudah disetel Major Masalah performa
C-8 Body respons dibaca habis lalu di-Close Blocker Koneksi tidak bisa dipakai ulang → bocor
C-9 Retry punya backoff + jitter + batas atas Major Badai retry
C-10 Operasi yang di-retry bersifat idempotent Blocker Pemotongan saldo ganda

D. Storage dan Persistensi(sesuai Fase 4)

# Item Pemeriksaan Level Masalah Khas
D-1 Flush() dipanggil sebelum Sync() Blocker Data masih di buffer user space
D-2 Record punya CRC/checksum yang bisa mendeteksi partial write Major Kerusakan diam-diam
D-3 Logika pemulihan bisa truncate saat menemukan kerusakan, bukan panic Blocker Crash saat startup
D-4 Penghapusan memakai tombstone, dan compaction membersihkannya Major Ruang tidak dikembalikan
D-5 Semua file handle di-defer Close Blocker Kebocoran fd
D-6 Klaim durability sesuai dengan perilaku aktual Major README bilang tahan mati listrik tapi tidak ada fsync
D-7 Penulisan konkuren diserialisasi(lock atau single writer) Blocker Log tercampur dan rusak
D-8 Ada test pemulihan(restart + injeksi kerusakan) Blocker Pemulihan tidak pernah diuji

E. Terdistribusi(sesuai Fase 5)

# Item Pemeriksaan Level Masalah Khas
E-1 Semua RPC punya timeout Blocker Menggantung selamanya
E-2 Deadline menurun di sepanjang rantai pemanggilan Major Timeout hilir > hulu
E-3 Turun tahta saat menerima term/epoch yang lebih tinggi Blocker Split brain
E-4 Ada fencing(tulisan dari leader lama ditolak) Blocker Double write
E-5 State kritis ditulis ke disk dulu baru merespons Blocker Sudah berjanji tapi belum dipersistensi
E-6 Minoritas menolak penulisan saat terjadi partisi Blocker Kehilangan data
E-7 Ada test injeksi kegagalan(bukan hanya menguji happy path) Major Kegagalan tidak pernah diuji
E-8 Menyatakan secara eksplisit level konsistensi dan kondisi kapan ia bisa dilanggar Major Menjanjikan terlalu banyak

F. Observability(sesuai Fase 6)

# Item Pemeriksaan Level Masalah Khas
F-1 Jalur kritis punya metrik(jumlah request, latensi, jumlah error) Major Berjalan sebagai kotak hitam
F-2 Kardinalitas label metrik terkendali(tanpa user_id / request_id) Major Menghancurkan Prometheus
F-3 Log terstruktur dan membawa request/trace id Major Tidak bisa dirangkaikan
F-4 Log tidak memuat informasi sensitif Blocker Membocorkan privasi
F-5 Log error tidak dicetak berulang di tiap lapis Minor Alert menenggelamkan informasi yang berguna
F-6 Ada metrik saturasi(kedalaman antrean, in-flight) Major Tidak ada peringatan sebelum overload

Beri skor(1–5) untuk setiap PR / setiap orang:

Dimensi 1 3 5
Ke-benaran Ada bug yang tidak ditemukan Happy path benar, batas kadang terlewat Batas, jalur kegagalan, dan konkurensi tercakup penuh serta punya test
Keamanan resource Ada kebocoran yang jelas Resource biasa semuanya ditutup Ada test deteksi kebocoran(fd/goroutine)
Keamanan konkurensi Ada data race Lolos -race Lolos -race -count=100 + tanpa kebocoran + ada backpressure
Desain kegagalan Hanya memikirkan jalur sukses Ada penanganan error Ada strategi timeout, retry, degradasi, dan pemulihan
Dapat diobservasi Tanpa log dan tanpa metrik Ada log dasar Metrik RED + log terstruktur + trace
Dapat diverifikasi Bilang "menurut saya lebih cepat" Ada benchmark Ada perbandingan benchstat sebelum/sesudah + bukti profile
Dokumentasi Tidak ada Ada README Ada diagram arsitektur + ADR + keterbatasan yang diketahui

Indikator kesehatan tim(dihitung tiap kuartal): - Tahap rata-rata ditemukannya masalah level Blocker(makin awal makin baik: swa-review > CI > review manual > produksi) - Rata-rata jumlah bolak-balik per PR(turun = standar sudah terinternalisasi) - Tingkat kelulusan quality gate -race / lint / coverage

7. Aturan Keputusan untuk Perdebatan yang Sering Muncul

Tiga hal yang tidak ada habisnya diperdebatkan dalam review, selesaikan dengan aturan:

Perdebatan Aturan Keputusan
"Pakai pointer atau value" Lihat ukuran dan semantik. ≤ 64B dan immutable pakai value; selain itu pakai pointer.Jika ada sengketa performa, benchmark yang menentukan
"Perlu komentar atau tidak" Komentar menjelaskan why, bukan what. Komentar yang mengulang isi kode harus dihapus
"Interface perlu didefinisikan dulu atau tidak" Konsumen yang mendefinisikan interface(consumer-driven).Jangan menambahkan interface di mana-mana hanya demi testing
"Error pakai %w atau %v" Pakai %w jika pemanggil perlu memutuskannya; pakai %v jika hanya menambah konteks untuk dibaca manusia
"Coverage harus berapa persen" Tidak ada angka seragam.Jalur kritis(konkurensi/persistensi/protokol) dituntut 90%+; kode glue CRUD tidak dituntut
"Pakai ORM atau tidak" Untuk kueri kompleks/performa sensitif pakai SQL mentah + sqlc; CRUD sederhana boleh pakai ORM.Jangan mencampur keduanya
"Apakah optimasi ini sepadan" Bicara dengan benchstat. Yang manfaatnya < 10% tapi menambah kompleksitas, jangan dikerjakan

.PHONY: all build test race bench cover lint fmt vet tidy clean profile trace

all: fmt vet lint test

    @mkdir -p $(BIN)
    $(GO) build -o $(BIN)/ ./...

test:
    $(GO) test -count=1 $(PKGS)

race:
    $(GO) test -race -count=1 $(PKGS)

# Simpan baseline: make bench-save

    $(GO) test -bench=. -benchmem -count=10 $(PKGS) > bench-base.txt
    @echo "saved bench-base.txt"

bench:
    $(GO) test -bench=. -benchmem -count=10 $(PKGS) > bench-new.txt
    @benchstat bench-base.txt bench-new.txt 2>/dev/null || cat bench-new.txt

cover:
    $(GO) test -covermode=atomic -coverprofile=cover.out $(PKGS)
    $(GO) tool cover -func=cover.out | tail -1

lint:
    golangci-lint run --timeout=5m

fmt:
    gofmt -w .
    goimports -w .

vet:
    $(GO) vet $(PKGS)

tidy:
    $(GO) mod tidy

profile:
    $(GO) test -bench=BenchmarkHot -cpuprofile=cpu.out -memprofile=mem.out -o bench.test .
    @echo "run: go tool pprof -http=:8080 cpu.out"

    $(GO) test -run TestX -trace=trace.out .
    @echo "run: go tool trace trace.out"

clean:
    rm -rf $(BIN) *.out bench-*.txt bench.test
